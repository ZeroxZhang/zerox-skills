## 来源 ID 冲突与去重——本场景的要害

这是唯一一处**并行写入会真实损坏研究包**的地方，规则必须清楚：

- 每条研究线用**自己的代号前缀**：`A001`、`B001`、`C001`……子代理的 ID 前缀写进 `tasks/<代号>.md` 的「存档要求」。
- 子代理**不改** `sources.md` / `report.md` / `plan.md`，只回传 ID 清单，主线程统一合并。
- 去重判定：
  - 同一 URL 且内容一致，或文件哈希相同 → 只留一个规范 ID，其余标「重复→规范 ID」；
  - 同一 URL 但内容已变 → 新 ID + 元数据 `supersedes` 指向旧 ID，旧版保留。
- 中断续跑：每个前缀从**现有最大序号**往后编，不复用、不留空洞。

## 推演：并行拆分是否合理

scoping.md 明确禁止过早拆分（别把「研究 X」拆成「X 概述 / X 技术 / X 应用」）。向量数据库选型的合理拆法是**按子问题**而非按对象：

| 代号 | 子问题 | 边界（不做什么） |
|---|---|---|
| A | 用户业务约束与硬指标（规模、延迟、运维能力） | 不碰产品功能对比 |
| B | 候选产品的能力与实测证据 | 不重复 A 的约束梳理 |
| C | 隐藏成本与退出风险（迁移、锁定、合规） | 不做正面功能评测 |

若拆成「Qdrant 调研 / Milvus 调研 / Weaviate 调研」，三条线会各自重复调研通用格局、来源大量重叠、最后拼不成矩阵——这是失败模式。
