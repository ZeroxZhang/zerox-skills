### 实跑中踩到的真实情况

| 情况 | skill 规定的处理 | 实际 |
|---|---|---|
| 内置网页搜索工具返回空 | 能力盘点 → 降级 | 改用 Brave 搜索页（HTTP）+ 已知权威 URL 作发现渠道 |
| `WebFetch` 返回模型处理过的摘要 | 完整度标 `summary`，不作逐字摘录依据 | 全程未用其返回当原文，采集一律走 `capture_source.py` |
| `openai.com/api/pricing/` HTTP 403 | 报错退出、不绕过、按 ⑤ 登记 metadata-only | ✓ 退出码 2，登记 A004 |
| `ai.google.dev/...` curl 得 302 | 换工具/换路径 | 改用 urllib 成功（A005） |
| Brave 检索 HTTP 429 + 验证码 | 不绕过、记为检索受限 | ✓ 记入日志；外部反证缺席写进「未解问题」 |
| 搜索结果标题/URL 错配致 404 | 不能只信搜索摘要 | 换可验证 URL 重取 |

### 质检抓出的内容层错误（非脚本问题）

1. `notes/A-pricing.md` 缓存倍率算错（写成 0.1，实为 0.025）→ 复算后改正，并发现「写入倍率一致、命中倍率不一致」这一新事实。
2. `analysis/normalize_cache_cost.py` 初版把不同档位型号的绝对价并排比较 → 改为「相对各自 input 牌价的倍数」才可比。

两处都是「数字要核对口径」要防的失败，被本 skill 的质检环节自己抓出——这是它工作正常的证据。

### 与静态推演的差距

- 场景 3 要求的「来源 ID 不冲突、重复来源正确合并」在本题得到部分验证：A/B 两条线用不同前缀，无冲突；但**没有出现需要去重的重复来源**（两家研究线的信源不重叠），合并逻辑未被真正压测。
