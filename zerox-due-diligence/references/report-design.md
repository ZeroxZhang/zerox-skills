# HTML 报告设计与编排

主报告服务于理解与决策，研究底稿服务于追溯。先完成证据分析，再做编辑与可视化；渲染器不会代替分析者挑选主线、核验事实或作出判断。减少过程信息时保留理解公司所需的背景与经营机制，不能把“可读”理解为只剩结论和图表。

## 交付分层

| 位置 | 应呈现的内容 |
| --- | --- |
| 主报告 HTML | 公司画像、产品与客户、交易和经营机制、收入成本逻辑、关键数据、市场与竞争、重要风险、决策条件，以及影响这些判断的关键限制；摘要可先给核心判断 |
| HTML 折叠证据附录 | 正文引用的证据出处与定位，供读者按需查证 |
| 同目录 `*-audit.md` | 实体与关系台账、模块适用性、研究完成范围、研报覆盖、评分覆盖、完整模块分析、声明核验、数据桥接、冲突、全部缺口、搜索日志、资料请求与访谈提纲 |
| CSV / JSON / 原件 | 可继续更新的台账、计算输入输出、授权范围内的资料 |

执行了什么、没有执行什么必须真实记录，但不必把过程写成正文的主要内容。若缺少集团财务、关键原件或最新必读研报会改变决策，应在对应分析旁清楚说明其影响，详细补证过程再放底稿。不得借“阅读体验”隐藏重大反证、监管限制或未解决的核心矛盾。

## 先建立理解，再展开判断

1. 用目的、主体和信息截止日确定报告回答的问题。例如商业合作应回答“合作价值来自哪里、谁签约、怎样控制履约风险”，不是默认回答“股票值得买吗”。
2. 从已有分析提炼一个主判断与少量支撑判断。摘要可先给结论及条件，但正文先让陌生读者认识公司，再分析增长、风险和合作价值。不先展示台账行数、检索次数、模块数量、覆盖百分比或“流程已完成”面板。
3. 按“公司是谁及发展沿革 → 创始人与核心合伙人 → 产品、客户及业务运转 → 营收与盈利 → 营销增长 → 竞争及替代 → 风险和决策”组织内容。除人物与公司身份分章等契约要求外，可按业务调整章节，不固定章数；公司导读可以用清楚的描述式标题，分析章节再用有依据的判断标题。不要为了“结论先行”跳过读者尚不知道的背景，也不要使用“模块07”这样的内部标签。
4. 首次出现DTC、闭环、小单快反、订阅等术语，解释其在目标公司的具体做法、参与者及边界。每节用连贯段落说明事实、机制及其意义，再配置图表；把零散的“结论/证据/缺口”条目改写为分析。没有可靠数字时仍可解释已知经营逻辑，并在相关环节标明未知。
5. 在结尾给出可执行的推进条件、待确认事项与暂停条件。不要把完整访谈问卷、资料请求表或搜索计划放入结尾正文。

Standard 或 Deep 按目标和目的选择分析篇幅；Quick压缩展开程度，仍应保留基本理解路径。没有固定字数、章节数或图数要求，但不能以短小、信息有限或合作目的为由省略公司与商业模式。

## 十一个理解问题

下列内容用于保证背景和机制不在编辑时丢失，不能直接作为过程检查表放进正文。每个主题在内容模型中对应一个 `explanation` 块，可自然分布在不同章节；渲染为普通小标题和段落。

| 主题 | 陌生读者应能回答 |
| --- | --- |
| `identity` | 这是一家什么公司？本报告研究品牌、集团还是具体法人，三者有什么关系？ |
| `history_team` | 它何时、由谁、因何创立，哪些团队或发展变化形成了今天的业务？ |
| `offering` | 它具体卖什么产品或服务，客户拿到什么？ |
| `customers_markets` | 谁使用、谁选择、谁付款，在哪里、通过什么渠道购买？客户定位与已验证客户分布有何区别？ |
| `transaction_flow` | 一笔代表性业务怎样从需求、下单或签约走到交付、收款和售后？ |
| `operating_model` | 公司自己做什么，合作方做什么，谁承担库存、质量、履约等关键责任？ |
| `revenue_costs` | 按什么收费，收入对应哪些主要成本与费用，利润和现金受什么机制影响？哪些结果尚未验证？ |
| `differentiation` | 客户为什么可能选择它而非替代方案？哪些是已观察的特点、公司说法或尚待验证的优势？ |
| `financial_performance` | 营收规模、构成、毛利率和净利率分别是多少或为何未知？每项属于谁、哪个期间、什么来源，是否只是GMV、估计或单体资料？ |
| `marketing` | 怎样通过渠道、内容投放与品牌触达客户，并形成获客、转化和复购？哪些只是可观察做法，哪些效果已有数据？ |
| `competition` | 主要竞品和替代方案是谁、为何选它们、哪些维度可同口径比较？目标在哪些条件下有差异或被替代？ |

事实有依据用 `supported`；只知道部分内容用 `partial` 并具体说明未知及影响；无法解释该主题用 `unknown` 并说明缺什么。状态反映正文解释的证据边界，不是给公司评分。公司自述即使有出处也需在文字中保留自述属性，不能用 `supported` 暗示独立核验。不得用“信息不足”概括替代已有事实，也不能凭行业惯例补全目标公司的机制。

写未知或沿用模块缺口前，先核对最新证据、原文与模块更新是否同步。“没有材料”“已有公司/第三方描述”“未独立验证”“关键细节未取得”是不同状态。可以按明确来源属性介绍已披露的机制，再说明验证与细节限制；不能因为可信度不够，就声称完全没有信息。

### 官网、团队与经营事实的取证

先直接访问相关官网原页：公司介绍、产品与价格、服务或退货条款、销售渠道、门店、品牌合作、活动、团队页面；再用登记、披露、独立报道等核验。官网是理解公司自述和可观察产品的直接来源，不自动证明经营效果；不能在原页可访问时只采用媒体转述。成功、失败、受限或未找到分别写台账和底稿，正文只保留影响理解的限制。

财务表现逐项处理营收总量、营收构成、毛利率与净利率。可比数字配图，单值配范围说明；缺失分别写明，不能用网站GMV、融资额、估值、单体亏损或行业规模替代集团营收和利润。营销分析同时说明渠道与具体做法、效果证据及数据缺口；粉丝数和曝光量不能直接推成销售转化。竞品分析先解释选择依据，再统一地区、客户需求、产品、价格、渠道和期间，不能用行业大盘图替代主要竞争对象。

## 内容模型与生成

初始化工作区会生成 `report-content.json`。新主报告使用 `version: "1.2"`，按照[模板](../templates/report-content.json)与[字段契约](../schemas/report-content.schema.json)填写内容，证据ID必须对应当前项目台账。只使用契约支持的字段和图表类型，不自行嵌入任意HTML或远程脚本。历史 `1.0/1.1` 报告可在 `draft` 检查中读取并提示升级，不能通过 `completed` 验收或直接用于新主报告构建。

```bash
python3 scripts/build_report.py \
  --project /tmp/dd-example \
  --content /tmp/dd-example/report-content.json \
  --output /tmp/dd-example/reports/report.html

python3 scripts/check_report.py \
  --project /tmp/dd-example \
  --report /tmp/dd-example/reports/report.html \
  --mode draft \
  --output /tmp/dd-example/reports/report-check.json
```

上述命令还生成 `/tmp/dd-example/reports/report-audit.md`。覆盖已有交付物时显式使用 `--overwrite`；先保留需要的历史版本。旧 `--sections` + `.md` 用法仅用于兼容底稿生成，不作为默认主报告工作流。

内容模型承载编辑后的分析，模块文件承载完整研究。两者的重要判断、范围和数字应一致；证据有更新时同时检查受影响的正文与图表。不要把旧HTML中的数字手改成与内容模型不同的版本。

## 解释与业务图的填写方式

完整结构以[初始化模板](../templates/report-content.json)为准。以下仅展示单个内容块的字段，包含占位符，不能直接交付；不得把示例证据ID或机制当作任何公司的事实。

```json
{
  "type": "explanation",
  "topic": "operating_model",
  "title": "{{读者能理解的经营分工标题}}",
  "text": "{{说明目标与合作方各做什么、各承担什么责任；事实旁保留引用}}",
  "status": "partial",
  "evidence_ids": ["E-0001"],
  "limitations": "{{具体说明哪些责任边界未知，以及对理解业务的影响}}"
}
```

十一个 `topic` 各出现一次，全局完整即可，不必各占一章。`supported` 需有证据，`limitations` 可以为空；`partial` 需有证据及非空限制；`unknown` 允许无证据，但必须说明具体未知与限制。检查器能识别覆盖与字段，不能判断一段话是否真正把问题讲清楚。

业务机制必须用至少一个 `purpose: "business_model"` 的 `process` 图解释，图中每步按 `basis` 标注 `evidence`、`company_claim`、`inference` 或 `unknown`。前三种有对应证据，`unknown` 可不填证据并写明未知。推断所引证据是推断依据，不等于已直接证实该环节。若交易机制整体未知，可用 `transaction_flow` 的 `unknown` 状态及具体限制说明原因，按契约免除业务图；其他未知仍需分别说明。合作推进流程或尽调流程不能算作业务图。

只有顺序有依据时使用 `ordering: "sequence"`（兼容默认值），显示箭头；先后关系未核实或只是展示经营环节时用 `ordering: "conceptual"`，呈现无箭头、无序号的关联图。不能一面承认现货、预售或结算顺序未知，一面用线性箭头暗示已确定。并行业务可以分图解释，不强行串成同一笔交易。

机制示意只解释有证据支持的典型步骤；没有具体订单证据，不得展示仿真的订单金额、时间、客户或履约结果。未知步骤可以保留在图中，不用“行业通常如此”补齐。除非来源支持全部顺序与关系，不暗示每笔交易都严格按图运行。

工作区模板采用 `{{待填写}}` 和 `null`，不会预置虚构数值；其状态刻意不能直接生成最终HTML。至少填入两个真实可比数值才可生成定量图；没有可比数据时移除该图，写明限制并采用有依据的定性表达。

支持的内容块为 `explanation`、`text`、`bullets`、`callout`、`table`、`metrics`、`chart`、`timeline`、`process`、`people`、`image`、`matrix`；图表为 `bar`、`line`、`donut`。`kind` 使用 `actual`、`estimate`、`forecast` 或 `company_claim`；仅图级可用 `mixed`，且每个点必须单独写 `kind`。每点可用 `period`、`evidence_ids` 覆盖图级信息。时间线 `status` 使用 `completed` 或 `planned`，日期作为文字保留其实际精度。

图表与指标的 `entity_id` 指向项目主体，行业数据用 `industry`。图表至少两个已知数值，最多24个点；构成图最多六项，不接受缺失或负值且总量须为正。表格单元格使用字符串，行列数量一致。章节ID用小写英文、数字与连字符，需以字母开头且全文唯一；保留ID与完整字段见[内容契约](../schemas/report-content.schema.json)。字段之外的事实支持关系、可比性及视觉含义仍需人工复核。

## 公司沿革、人物与真实图片

在 `identity` 同章放 `timeline`，标 `purpose: "company_history"`，至少两个有日期、内容和引用的发展事件。优先选择创立、重要产品、业务转型、关键融资或渠道扩张等对业务有解释力的节点；区别法人注册、品牌创立和集团重组。计划节点明确标记，不能凑成已发生历史。只有 `history_team` 为 `partial/unknown` 且具体说明限制时可缺图，检查会警告，人工仍须确认确实不足两个事件。

创始人与核心合伙人、关键团队用独立于公司身份的章节介绍。`people.profiles` 每人分别写姓名、角色、适用期间、相关背景、具体贡献、限制和引用；不要把公司宣传中的名校或前雇主名单直接变成能力判断，也不要把职称直接当作贡献。资料不足可以删去人物块并在沿革说明未知，检查给警告；禁止拼接同名人物或补造团队故事。

图片应帮助识别公司、理解产品或渠道，例如真实标识、官网产品页面、门店或授权人物图片。先实际取得文件，再填写 `image` 的项目相对路径、角色、标题、替代文字、图注、出处、取得日期、使用说明和证据。有原页时 `source_url` 填安全HTTP(S)地址；本地或用户提供材料无原页时允许为空字符串，用 `evidence_ids` 关联原文件与来源台账，`usage_note` 说明提供者和使用范围。`captured_at` 是本次实际取得或读取素材的日期，不是原图拍摄日或页面发布日期；原始内容时点未知时在图注说明。模板仅有占位符，未取到图片就删除，不用生成图片冒充官网、产品或人物。

图片仅限 PNG/JPEG/WebP，每张≤5 MiB、全部合计≤15 MiB，构建后内嵌为离线HTML。运行时不支持SVG，禁止路径越界、越界符号链接和运行时远程图像；不能把远程URL填写成文件路径。若原始标识为SVG，可用可信渲染或浏览器截图另存位图并保留原始出处，不得重新生成冒充原标识。按实际材料说明使用范围，敏感图片遵守已有授权。官网截图能够展示页面当时的内容，不等于验证公司宣传、人物身份或经营实绩；证据仍须核查支持范围。

## 比较矩阵

使用 `matrix` 对竞品、营销渠道或财务口径做有解释力的比较。至少两列、每行单元格与列数一致，逐格填写文字、`basis` 与引用。`evidence/company_claim/inference` 须有依据；`unknown` 可无引用但清楚说明缺什么。用 `note` 说明选取对象、共同口径和无法比较的范围。不要用空白、问号或颜色暗示优劣，也不能混用不同地区、时期和定义进行排名。

矩阵适合定性机制或范围比较，不计作定量图。若已有可靠收入、价格、增速或构成数值，应另选适当数字图，矩阵不能成为少画数据图的理由。行业市场容量提供背景，仍需单独说明目标公司的主要竞争对象和替代关系。

## 数字与图形

有可靠数据的核心数字分析应图示，不能让读者在大段文字或密集表格里自行寻找规律。先确定读者需要理解的问题，再选择表达方式；不要只绘制易获得的数字，却让交易过程与经营分工留在抽象标签里。业务流程图解释公司怎样运转，定量图解释规模、变化与比较，两者承担不同任务；不要用图表数量代替分析质量。

| 分析问题 | 适合的表达 | 必须避免 |
| --- | --- | --- |
| 同口径随时间变化 | 趋势图，明确实际与预测区间 | 把不同数据商、不同主体、不同时间范围连成曲线 |
| 可比对象或阶段的规模 | 条形图，统一单位与比较基准 | 不同单位共轴，条形图截断零基线夸大差异 |
| 有完整分母的构成 | 构成图，标明总体与分类规则 | 类别重叠或缺项却画成完整百分比，零值与缺失混用 |
| 单个关键值 | 指标卡配范围和解释 | 给不可评分项目虚构综合分，拿样本量当公司实力 |
| 股权、合同或业务关系 | 关系图或流程图，区分已证实与待证实 | 将推断关系画成已核实控制，借布局暗示担保 |
| 一笔业务如何运转 | 业务机制图：客户需求、购买、提供产品/服务、交付、收费与售后；标出参与者及证据属性 | 用合作推进图代替经营机制，把常见行业做法当目标事实，或将示意冒充真实订单 |
| 事件与扩张节奏 | 时间线，标记已发生、计划和未确认 | 把计划开业、拟收购或预测当成已完成 |
| 团队及核心分工 | 独立人物卡，说明角色期间、背景、具体贡献与限制 | 拼接同名履历、把职称当贡献 |
| 竞品、营销渠道或财务口径 | 逐格标注依据的比较矩阵，可靠数字另配图 | 把定性标签当评分、以行业空间替代竞品 |
| 产品、官网和门店的可观察外观 | 有来源与说明的真实图片 | 造图冒充实物、把截图宣传当已验证事实 |
| 多口径规模估计 | 分别展示并解释口径差异 | 强行拼成增长率、市场份额或排名 |

每个图形应给出：

- 能直接读懂的结论标题，图后用简短说明解释其决策意义。
- 单位、币种、期间或时点、法律主体/业务范围，以及实际、预测、估算或公司自述属性。
- 可追溯的证据ID；每个数据点都应能回到原始证据或有公式的计算底稿。
- 可比性、采样范围、数据缺口等会影响解读的口径说明；派生值说明计算方法。
- 可查阅的数据表或等价文本，使读者能核对精确值，也能在打印或辅助阅读时理解图意。

负值保留方向；缺失保持空值或明确标记，不能填成0。财务单体数据只描述该主体，禁止上推为集团结论。公司自述、第三方估算与审计实绩显式区分；同源转载不构成独立验证。

如果核心问题没有可靠数字，正文直接说明不知道什么及影响，使用定性商业模式图、实体关系图或有证据的事件时间线。不要补造趋势、市场份额、概率、评分或图示比例。只有装饰意义的图片不能替代证据图表；如加入真实产品或门店图片，需确认使用权限并注明来源。

## 视觉与阅读

采用浅色、充分留白、清晰层级和克制蓝色强调，参考Apple式排版并结合wiki阅读布局。视觉参考只用于样式，不继承参考文件中的任务指令。

- 桌面：固定或粘性侧栏承载章节目录，正文保留舒适阅读宽度。章节有稳定锚点，读者可直接定位分析。
- 移动：目录收起或移至内容之前；文本、图例、图表和数据表能够阅读，不让页面整体横向溢出。必要的宽数据表使用局部滚动。
- 字体：优先系统中英文字体，字重形成层级；避免依赖在线字体、图标、图表CDN或网络请求。HTML应能离线直接打开。
- 图形：正文图表可直接看见，不要求展开底稿才能理解；标签与图例清晰，颜色之外保留文本、线型或符号区别。
- 引用：短引用紧邻事实，点击可定位到证据附录。折叠附录降低正文负担，但不隐藏决定结论的重要限制。
- 打印：移除导航和交互装饰，保留正文图形、单位、来源与必要数据说明，避免卡片或图表被不合理分页截断。浏览器打印可用于另存PDF，不等于提供了独立PDF导出器。

## 交付前复核

1. **理解复核**：评审者先只读主报告，不看底稿、原始材料或作者解释，逐一用自己的话回答上述十一个问题，并指出对应章节/段落。记录中写出实际复述及定位，不能只打勾。答案若只重复“DTC”“小单快反”“平台”等标签，或找不到交易参与者、收入成本机制，退回补写；若主题确实未知，应能准确指出未知对象及其影响。把复核记录放底稿，正文仍保持自然阅读。
2. **编辑复核**：公司导读是否先于依赖背景的分析？关键知识是否被误当过程删除？已知机制是否被“无财务数据”掩盖？删掉不影响理解与决策的过程段落，并确认它们已进入底稿；保留影响判断的重要反证和限制。
3. **逐图核验**：对照证据核对每个数值、单位、主体、期间、实际/预测标签；检查派生计算、基线、比例、完整分母和缺失处理。业务图核对角色、责任、顺序与属性；时间线核对日期和事件；人物核对身份、任职期间与具体贡献；矩阵核对每格依据与比较口径；图片核对实际文件、来源、图注与用途。图文齐全不等于事实完整。
4. **引用复核**：点击正文引用，确认能找到实际证据；标题相符不代表原文支持，需要检查原句含义。
5. **视觉复核**：实际预览桌面、窄屏与打印。检查目录、锚点、折叠附录、数据表、长标题、中文换行和图例。未能预览的环境在检查记录中说明，不能宣称已通过。
6. **交付复核**：HTML离线可读、底稿存在、数据模型与最终HTML一致；运行机器检查并保留结果。结构通过不等于理解通过，不能用十一个主题字段齐全代替实际复述。重要限制应出现在正文中，而不只是底稿中。
