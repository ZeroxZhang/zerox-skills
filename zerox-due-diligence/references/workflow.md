# 执行工作流

首先读取本文件、[证据标准](evidence-standard.md)和[目的手册](purpose-playbooks.md)。数据字段以[契约](../schemas/data-contract.json)为准。

## 输入与澄清

| 字段 | 要求 |
|---|---|
| target | 目标名称；尽量包含法定全称、官网、注册地、信用代码/注册号或证券代码 |
| purpose | 公司研究 company_research，或投资、并购、战略/商业合作、客户授信、供应商准入、竞品研究六类专项；仅真实目的未定时为空 |
| depth | Quick / Standard / Deep，默认 Standard；控制范围、历史跨度、分析粒度和验证强度，访问权限另记 |
| geography | 注册地、主要经营地、交易相关司法辖区 |
| focus | 约定研究范围、用户关键问题及重大性；有具体交易/合作时再记录方式与规模 |
| materials | 已有 BP、财报、合同、报告和用户可用数据库 |
| as_of_date | 信息截止日期；注明是否为历史时点研究 |
| constraints | 时限、预算、工具、访问权限、输出语言与格式 |

目标主体存在歧义时，先列出候选并询问最少必要信息；不得任选一个主体开展实质判断。可以继续不依赖实体选择的研究准备。

“全面了解这家公司”等请求已明确指向 `company_research`，不要求用户另选交易目的。目的确实有分歧时，一次询问不超过三个关键问题，并继续不依赖答案的基础研究；尚未明确时 `purpose` 保持空值。深度未给出按 Standard 并明示范围。先解释公司，再按目的加载专项；不擅自假设投资授权、交易安排或授信额度。

## 阶段推进

每阶段写清输入、动作、产出、完成条件和失败处理。

| 阶段 | 必须完成的动作 | 产出/退出条件 |
|---|---|---|
| Phase 0 范围与能力 | 明确目标、目的、深度、基准日、重大性及哪些问题必须回答；访问权限单独确认 | 项目配置、约定范围与能力限制；不虚构联网或数据库能力 |
| Phase 1 实体与控制链 | 锁定法律主体/品牌/集团边界、股权与控制关系、上市状态 | 主体表与控制链；有歧义则暂停依赖该身份的结论 |
| Phase 2 研究设计 | 先覆盖共同研究骨架，再按重要性选择待深入问题；制定来源、正反证与停止条件，基础扫描后更新 | 检索计划、待验证声明、适用模块与上市研报触发结果；不把早期假设当定论 |
| Phase 3 官方与基础资料 | 直接阅读相关官网公司、产品、条款、团队与渠道页面；取得登记、披露、财报、监管、司法等原件，合法取得有解释力的真实图片 | 来源与证据台账、原页与图片定位、版本/口径记录；访问失败需登记，不以媒体转述假充官网已读 |
| Phase 4 强制研报流程 | 对上市公司或上市子公司执行[模块18](modules/18-listed-company-research.md)专门流程；其他目标按行业相关性检索 | 报告目录、全文获取状态、逐份阅读、最新性和覆盖差距 |
| Phase 5 模块分析 | 按关键问题连接历史、组织、业务、行业、竞争和财务；比较当前解释与替代解释，选择能区分它们的证据 | 有依据的机制与变化解释、关键结论、反证和缺口；未知逐项说明，不以行业数据替代公司表现 |
| Phase 6 核验与冲突 | 核对主体/时间/口径/同源；检验目标方声明和研报核心假设 | 声明核验表、冲突表、估算底稿 |
| Phase 7 研究判断 | 复核关键结论、风险、情景和剩余缺口影响；专项再形成决策条件，评分仅显式启用 | 目的适配判断、完成复核与补证条件；关键问题不可判则保持受限 |
| Phase 8 报告与校验 | 按1.2契约编排十一主题、公司时间线、独立人物章节、业务图及适用图片/矩阵，生成HTML及底稿，执行结构、只读正文理解、事实与视觉复核 | 可阅读的HTML、完整audit.md及检查结果；逐项核查允许的缺图缺资料例外，约定范围未完成则保留受限状态 |
| Phase 9 交付与补充 | 交付HTML、底稿、台账及更新触发条件；资料请求和访谈提纲放底稿 | 读者直接获得判断与行动条件；核验者可追溯依据和未完成工作 |

研究中可并行分工，但实体 ID、信息截止日、币种/单位、标签与证据规范必须共享。合并时统一编号、同源去重、处理冲突；不能直接拼接多份互相矛盾的子报告。

阶段可迭代：发现新母公司、重大事件或关键矛盾，应回到相关阶段补证，而不是在最终摘要中悄悄消除问题。

### 关键问题的迭代

基础扫描后，将会改变公司理解或专项决策的问题排序；优先深入影响大、证据薄弱且可通过新增信息区分的问题。为每个关键问题明确当前解释、合理替代解释、区分证据和改变判断的条件。不要只检索“支持公司好/坏”的材料，也不为普通事实强造相反观点。

沿用 `claim-register`：当前陈述放 `statement`，成立前提与替代解释写 `assumptions`，反证及区分检验写 `counterevidence`，尚未解决与改变判断条件写 `unresolved`；实际取得的支持/反驳证据通过 `claim-evidence` 关联，待取信息进入 `gap-register`。没有反证材料时写清已查范围和剩余验证，不将“未找到”写成证实。

模块分析回到同一解释链：外部需求与供给怎样影响公司选择，组织与资源如何支持执行，执行如何形成营收、利润与现金。证据无法支持某环时限定结论，并将该缺口对后续判断的影响保留下来。

### 工具与访问失败

- 有联网：访问原始出处并记录真实检索，不仅采集搜索结果。
- 无联网：仅分析已有资料，标为“离线材料分析”；给可执行补查计划，不声称掌握最新情况。
- 有代码环境：运行脚本并记录真实结果；无代码环境：按同一数据契约人工处理，注明未运行自动校验。
- PDF/扫描件不可读：尝试合法下载、OCR 或表格核验；无法确认的文字、数字、页码不得引用为已读证据。
- 资料付费或需授权：记录障碍，检索合法公开替代，列出需用户提供或授权的具体资料。
- 工具失败不自动取消强制检索或改写阅读状态。继续不受影响的分析，研报覆盖和约定研究范围分别按实际证据判断。

## 实际项目操作

1. 用 `init_project.py` 在技能包外新建工作区；目标/目的/日期写入配置。`scoring_enabled` 默认 false；公司研究和目的未定不评分。
2. `entity-map.csv` 一行一实体；多层/多关系用 `entity-relations.csv` 一行一边。身份 resolved 需注册号（品牌/分部用可核验内部标识）与证据；关系 verified 需证据和有效日期。区间采用 `[effective_from, effective_to)`，终止日即不再控制；拟议交易不算已控制。
3. `control_chain_checked` 与 `control_evidence_ids` 记录核验依据，不能靠一次无结果自动勾选。登记事件、行业词、语言和模块适用性；用 `sync-coverage` 预建必要类别与缺口。
4. `search_plan.py` 输出计划后再实际检索，成功/未找到/失败分别写入 `search-log.csv`。未执行计划不能作为执行日志。
5. 原件存 `materials/` 或授权定位；真实图片建议存 `materials/images/`，记录可用原页URL或本地材料出处、本次取得/读取日期与使用范围。证据和声明通过关联表连接。添加互相引用数据可用批量 JSON，一次校验后写入；每次更新保留 `.ledger-backup-*`，多文件写入非数据库事务，中断时从完整快照恢复。
6. 模块结论写入 `modules/01-名称.md` 等；资料请求和访谈围绕开放缺口定制。财务计算按需运行。专项启用评分前，确认 `scoring_override` 的项目权重和关键维度；不用商业得分抵销风险。
7. 阅读[报告设计](report-design.md)，填写1.2版 `report-content.json`：十一解释主题各出现一次；公司时间线与身份同章，创始人与核心合伙人资料单列章节，再讲业务、营收与盈利、营销、竞争及决策。图片必须替换成实际取得的项目文件，否则删去占位块；矩阵逐格标注依据。不要直接把模块Markdown或CSV台账复制为正文。可靠数字须提供适当图表，未知保留具体范围，不能造数或拿装饰图替代。
8. 用 `build_report.py --project <工作区> --content <工作区>/report-content.json --output <工作区>/reports/report.html` 生成离线HTML和同目录 `report-audit.md`。主报告保留必要的判断边界，核验过程与请求清单进入底稿，完整证据可通过HTML末尾的折叠附录查阅。
9. `check_report.py` 校验HTML后，人工核对关键引用、图表口径、时间线日期、人物角色贡献、图片出处与矩阵可比性；只读正文复述十一问题，预览桌面、移动和打印效果。历史1.0/1.1仅可草稿检查，新建及完成态要求1.2。按[质量门槛](quality-gates.md)复核约定研究范围；关键问题不可判断时保留 draft/limited，不能用脚本通过代替研究完成。
10. 交付HTML、底稿、原始台账、计算底稿与补齐路径。更新触发可包含新财报、重大事件、控制变化、报告修订、信用或履约变化；未额外授权不建立自动监控。

## 三种完成口径

- `research_gate` 仅表示必读资料的获取、阅读与覆盖，严格按模块18计算；范围完成不能将其改为 complete。
- `report_status=complete` 表示约定研究范围完成。填写 `completion_review` 的范围、关键声明、所有开放缺口的影响与处置、复核时间；关键结论须有支持证据，阻断核心问题的缺口仍要求 limited。详见[质量门槛](quality-gates.md)。
- `declared_complete` 表示所有必需动作完成；存在开放缺口或尚未执行动作时不得声明。完成约定范围不等于所有资料和动作齐备。
