# skill 编写规范

新增或修改套件成员前必读。硬约束同时写在 `AGENTS.md`，此处展开写法与判据。

## 1. 命名与目录

- 目录名 == frontmatter `name`；小写英文、数字、连字符，少于 64 字符。
- 成员一律 `zerox-*`；路由 `zerox`。成员资格以 `registry.md` 为准，不靠前缀判定（套件外另有 4 个 `zerox-*` 个人 skill 共享前缀）。
- 技能真源必须是套件目录的直接一级子目录（见 `docs/architecture.md` §4）。

## 2. frontmatter 契约

只两字段，不默认加版本号：

```yaml
---
name: zerox-<能力或场景>
description: <能力陈述>。<触发条件与触发词>。<边界句>
---
```

- **能力陈述**：它直接产生什么交付或必要中间判断。
- **触发条件**：写清「用户要求…时使用」这类触发句与触发词，覆盖口语别名。
- **边界句**：近邻任务易误触发时必须写（例：「不适用于单张图表、纯文案改写」）。
- 建议 ≤300 字符，上限 1024。中文行文照《中文文案排版指北》。

## 3. 解剖结构

```
zerox-<name>/
├── SKILL.md        # 必备入口：共同决策、关键流程、停止条件
├── references/     # 条件性方法 / 标准 / 案例，状态触发才读
├── scripts/        # 重复、确定、需可靠执行的操作
└── assets/         # 进入最终交付的模板 / 字体 / 骨架
```

只建真正用到的目录。**不建**空目录、占位 README、changelog、重复说明。

## 4. 入口纪律

- SKILL.md ≤300 行；超了就把条件性内容下放 `references/`。
- 用「状态 → reference 分发表」做渐进披露（表格式见脚手架）：`当前状态 | 该做什么 | 读哪个 references/`。
- 入口保留：任务与边界、不变量、状态判据、最小提问条件、核心流程、停止条件、每个 reference 的读取条件。

## 5. 路由交互契约

- 叶子 skill **禁止**指名、调用或引导用户去跑兄弟 skill（「建议你先用 /zerox-x」这类一律不允许）。
- 跨 skill 只允许**只读** `../zerox-<能力>/references/` 下的方法文档，不复制正文。
- 收尾只保留条件式提示：「若还需…，回到 `/zerox` 重新编排」。
- 编排只发生在路由 `zerox` 与场景流水线层。

## 6. 组合契约（供路由与流水线使用）

- 1 主 + ≤2 辅；辅助角色仅三种：前置筛选 / 证据补充 / 验收约束。
- 单一任务、单一交付物；最终只交付一份由主 skill 统领的结果，禁止依次拼接多份报告。
- 顺序由依赖决定：淘汰方向的前置筛选先跑，证据补充在主结论前，验收约束在定稿前。
- 显式写出提前停止条件与权限边界。

## 7. 交付契约

动工前先写 `templates/task-contract.md` 实例并对齐：目标与决策用途 / 受众与汇报场景 / 最终交付物 / 证据要求 / 验收标准 / 边界 / 约束。需求变更先改契约再改产出，验收以契约为准。

## 8. 质量验证四级

只报实际达到的最高级，不越级声称：

1. **结构校验**：frontmatter 合规、目录齐、无占位符、无绝对本地路径、references 引用可达
2. **行为冒烟**：真实输入跑通主流程与边界句（近邻任务确实不触发）
3. **留出 / 回归**：改动能解释一类稳定失败；复测留出样本（执行者未见过预期答案）
4. **安装交付**：`bridge-skill.sh link` 整套接入后可触发，references 按需可达

## 9. 从槽位到可用

1. `registry.md` 确认槽位、职责与边界（没有槽位先补表再动手）
2. `cp -r templates/skill-template zerox-<name>`，`skill-skeleton.md` → `SKILL.md`
3. 按本文填实正文与 references
4. `registry.md` 状态翻「已建」、填路径
5. `~/.claude/skills/dbs-bridge/scripts/bridge-skill.sh link /Volumes/Out/my_own_skills/zerox-skills`
6. 走四级验证，报告实际达到的级别
